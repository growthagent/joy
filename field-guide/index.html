What Joy is

Joy is a framework for building web apps in Roc. Your app compiles to WebAssembly and runs in the browser, and the same Roc code that draws a page there can draw it on the server.

A Joy app is written in the shape that Elm made popular, often called The Elm Architecture. All of the app's state lives in one value, the model. Things that happen arrive as messages. A function called update turns a model and a message into the next model, and a function called render turns a model into HTML. Joy does the rest: it listens for events, calls your functions, and changes only the parts of the page that need to change.

What you get

  • The platform. The Roc platform your app runs on. It gives you effects and subscriptions for HTTP, timers, the keyboard, the DOM, ports to JavaScript, Web Crypto and media recording.
  • joy-html. A package with the Html and Attribute types. The server and the browser use the same types, so one view can be rendered on either side.
  • joy.js. The one script a page includes: the runtime that runs a bundle, with the browser code of the features your bundles call, and the few lines that mount every bundle the page names. runtime.js is the same runtime as a library, for embedding a bundle by hand.
  • ./joy. The command line. It finds the bundles in your project, builds them, hot reloads them into open pages while you work, and keeps your app and itself on a Joy release.

How this guide is laid out

Start here builds a browser app one idea at a time: the update loop, views, effects, subscriptions and flags. Growing an app covers what changes when an app has several pages and a server: three folders, server rendering, bundles, routes and typed endpoints. Structuring for scale is about the decisions that keep a large app pleasant to work in: how to reuse a piece of UI, when something should have its own model, and how to let types do the checking for you. Much of that part comes from the Elm community, where these questions were worked out first.

Your first app

A Joy app is one Roc file that names its platform and provides six things: Model, Msg, init, update, render and subscriptions.

The header

The first lines say which platform the app runs on and which packages it uses. Every Joy app needs Joy's platform as pf and joy-html as html.

app [Model, Msg, init, update, render, subscriptions] {
    pf: platform "https://github.com/niclas-ahden/joy/releases/download/VERSION/HASH.tar.zst",
    html: "https://github.com/niclas-ahden/joy-html/releases/download/0.17.0/AcmwFzyfbsf5RALWNdX6cXw1cuuDXt96YfcysNqgFqoG.tar.zst",
}

Take the platform URL from the latest release on the Joy releases page. The examples inside the Joy repository use pf: platform "../platform/main.roc" instead, so they build against the checkout.

A counter

import html.Html exposing [div, button, text]
import html.Attribute exposing [id, on_click]
import pf.Effect

Model : { count : I64 }

Msg : [Increment, Decrement]

subscriptions = |_model| []

init : Str -> (Model, List(Effect(Msg)))
init = |_flags| ({ count: 0 }, [])

update : Model, Msg -> (Model, List(Effect(Msg)))
update = |model, msg|
    match msg {
        Increment => ({ count: model.count + 1 }, [])
        Decrement => ({ count: model.count - 1 }, [])
    }

render : Model -> Html(Msg)
render = |model|
    div(
        [],
        [
            button([id("increment"), on_click(Increment)], [text("+")]),
            text(model.count.to_str()),
            button([id("decrement"), on_click(Decrement)], [text("-")]),
        ],
    )

The six parts

PartWhat it is
ModelEverything the app knows. Here a single count.
MsgEverything that can happen, as a tag union. Here two buttons.
initThe first model, and any effects to start with. It receives the app's flags as a string (see Flags).
updateThe next model after a message, and the effects to run.
renderThe page for a model. It is called again after every update.
subscriptionsThe outside events the app wants to hear about right now, like a timer. Here none.

update and render are plain functions. They read their arguments and return values, and they cannot fetch data, start timers or touch the DOM. Anything like that is an effect: a value update returns and Joy carries out. That one rule is why a Joy app is easy to follow. To know how the app got into a state, you only need to look at the messages it received.

A file like this one is what Joy calls a bundle: an app on the Joy platform, one file that becomes one wasm. ./joy build finds every bundle in client/ by that header and builds it, and a page can hold one or several. Bundles, under Growing an app, has the whole of it. For now one file is the whole app.

Running it

The page that shows the app is a plain HTML file in public/. It has an element that names the bundle and loads joy.js, as Flags shows. Then start the development loop:

$ ./joy dev

The app is now at http://localhost:8000. Save client/counter.roc and the open page takes the new build without a reload: the count you clicked up to stays. A build that fails shows roc's report over the page until the next one succeeds. The ./joy command, under Reference, has the rest.

The update loop

Every Joy app runs the same loop. Knowing it by heart makes every other topic in this guide easier.

Model→ render(model)→ Html(Msg)→ Joy updates the page→ a click, a keypress, an answer→ Msg→ update(model, msg)→ (Model, effects)↺

Highlighted steps are the functions you write. Joy does everything else.

  1. Joy calls render with the current model and gets back a tree of Html(Msg).
  2. Joy compares it with the last tree and changes only what differs on the page.
  3. Something happens: the user clicks a button that carries on_click(Increment), a timer fires, or an HTTP request answers. Each of these becomes a message.
  4. Joy calls update with the model and the message. You return the next model and a list of effects.
  5. Joy runs the effects. When one of them finishes, its result comes back as another message, through step 3.

What follows from it

  • One source of truth. The page is always render(model). There is no hidden state in the DOM that the model does not know about.
  • Effects are data. update describes what should happen. Joy decides when and how. That makes update easy to test: call it and look at what it returns.
  • Messages are the history. Every change to the model came from a message, so a list of messages explains how the app got where it is.

Views

Views are built with joy-html. An element is a function that takes a list of attributes and a list of children.

import html.Html exposing [div, h1, input, label, p, text]
import html.Attribute exposing [class, for_, id, on_input, value]

search_box : Str -> Html(Msg)
search_box = |query|
    div(
        [class("search")],
        [
            label([for_("query")], [text("Search")]),
            input([id("query"), value(query), on_input(|typed| UserTypedQuery(typed))]),
        ],
    )

Events are attributes that carry a message. on_click(UserClickedSave) sends a message as it is. on_input and other events that come with a value take a function from the value to a message.

The type tells you what a view can do

Look at the type a view returns:

  • Html(Msg) can send the messages of Msg. It may have buttons, inputs or links that do something.
  • Html(msg) with a lowercase type variable can send nothing. It works inside any page because it never produces a message of its own. A heading, a price, an error text.
## Inert: works on any page, can never send a message.
price_tag : I64 -> Html(msg)
price_tag = |kronor| p([class("price")], [text("${kronor.to_str()} kr")])

Use the lowercase form whenever a view has no events. Readers learn something at a glance, and the view can be used on any page without wrapping.

Html.map

When a part of the page has its own message type, Html.map wraps every message it sends into a message of the page:

Html.map(Counter.view(model.counter), |m| Counter(m))

You will see this whenever an app is split into pages, in Pages, and when a piece of UI has its own state, in Components.

Effects

An effect is a description of something to do: send a request, wait, open a dialog. update returns effects, and Joy runs them.

import pf.Effect
import pf.Http

Model : { quote : [NotRequestedYet, Loading, Loaded(Str), Error(Str)] }

Msg : [
    UserRequestedQuote,
    GotQuote(Try(Http.Response, [HttpErr([Timeout, NetworkError])])),
]

update : Model, Msg -> (Model, List(Effect(Msg)))
update = |_model, msg|
    match msg {
        UserRequestedQuote =>
            ({ quote: Loading }, [Http.get("https://example.com/quote", |result| GotQuote(result))])

        GotQuote(Ok(response)) =>
            ({ quote: Loaded(Str.from_utf8_lossy(response.body)) }, [])

        GotQuote(Err(HttpErr(Timeout))) => ({ quote: Error("The request timed out") }, [])
        GotQuote(Err(HttpErr(NetworkError))) => ({ quote: Error("The request never completed") }, [])
    }

The model changes to Loading at once, and the request goes out. When it answers, its result arrives as GotQuote. Notice that the quote's state is one tag union, not a loading flag plus an error string. More on that in State as types.

A debounce

A search field should not send a request on every keystroke. Time.debounce restarts a named timer each time it is returned, so only the last keystroke in a pause gets through:

UserTypedQuery(query) =>
    ({ ..model, query }, [Time.debounce("search", 200, |_| UserPausedTyping)])

UserPausedTyping =>
    (model, [Http.get(search_url(model.query), |result| ServerAnsweredSearch(result))])

Effect.map

Like Html.map, Effect.map changes the message an effect will produce. You need it when a page or component returns effects of its own message type:

effects.map(|effect| Effect.map(effect, |m| Counter(m)))

Subscriptions

An effect happens once. A subscription keeps sending messages for as long as the app asks for it.

After every update Joy calls subscriptions with the new model. Whatever list it returns is what the app listens to from then on. A subscription you stop returning is stopped.

import pf.Keyboard
import pf.Sub
import pf.Time

subscriptions : Model -> List(Sub(Msg))
subscriptions = |model| {
    ticking = if model.running [Time.every(1000, |now| Tick(now))] else []
    escape = if model.dialog_open [Keyboard.on_down_keys(["Escape"], |_| UserPressedEscape)] else []
    ticking.concat(escape)
}

The clock ticks only while running is true, and Escape is only heard while the dialog is open. Because subscriptions follow the model, they can never get out of step with it. The same holds for the microphone in pf.Media: it is open exactly while the app subscribes to it.

Sub.map wraps a subscription's messages, the same way Html.map and Effect.map do.

Flags

Flags are the data an app starts from. The page writes them on the bundle's root element, and init receives them as a string.

<div data-joy-bundle="app" data-joy-flags='{"name": "Brödil", "karma": 99}'></div>
<script type="module" src="./joy.js"></script>

joy.js is the loader ./joy build writes next to your bundles, with the runtime built into it, so it is the only script a page loads. The build copies public/ in beside it, which is why the page can name it as ./joy.js. It mounts a bundle on every element that names one, with the flags on that element, by calling the runtime's mount. You can import mount from runtime.js and call it yourself instead when you embed a bundle by hand.

Flags are usually JSON. Json.parse decodes them into the type the code expects, and a mismatch is an error you can show instead of a crash:

Model : [
    Human({ name : Str, karma : I32 }),
    FailedToParseFlags(Str),
]

init : Str -> (Model, List(Effect(Msg)))
init = |flags|
    match Json.parse(flags) {
        Ok({ name, karma }) => (Human({ name, karma }), [])
        Err(problem) => (
            FailedToParseFlags(flags),
            [Console.log("Could not read the flags: ${Str.inspect(problem)}")],
        )
    }

In a full-stack app the flags are the page's model: the server builds it, writes it on the bundle's root, and the client starts from exactly that value. That is how hydration works, in Server rendering.

Growing an app

Pages

When an app grows, split it into pages. A page is a module with its own Model, Msg, init, update, view and subscriptions. It is the same shape as an app, only the app calls it instead of the platform.

import html.Html exposing [button, div, text]
import html.Attribute exposing [on_click]
import pf.Effect
import pf.Sub

Counter := [].{
    Model : { count : I64 }

    Msg : [UserClickedIncrement, UserClickedDecrement]

    init : {} -> (Model, List(Effect(Msg)))
    init = |_| ({ count: 0 }, [])

    update : Model, Msg -> (Model, List(Effect(Msg)))
    update = |model, msg|
        match msg {
            UserClickedIncrement => ({ count: model.count + 1 }, [])
            UserClickedDecrement => ({ count: model.count - 1 }, [])
        }

    subscriptions : Model -> List(Sub(Msg))
    subscriptions = |_model| []

    view : Model -> Html(Msg)
    view = |model|
        div([], [
            button([on_click(UserClickedDecrement)], [text("-")]),
            text(model.count.to_str()),
            button([on_click(UserClickedIncrement)], [text("+")]),
        ])
}

A module's type is named after its file, so Counter.roc holds Counter := [].{ ... }, and other modules refer to Counter.Model and Counter.update.

Putting pages together

The app's model says which page is showing and holds that page's model. Its messages wrap each page's messages in a tag:

Model : [
    Counter(Counter.Model),
    Clock(Clock.Model),
]

Msg : [
    Counter(Counter.Msg),
    Clock(Clock.Msg),
]

update : Model, Msg -> (Model, List(Effect(Msg)))
update = |model, msg|
    match (model, msg) {
        (Counter(c), Counter(m)) => Update.map(Counter.update(c, m), |x| Counter(x), |x| Counter(x))
        (Clock(c), Clock(m)) => Update.map(Clock.update(c, m), |x| Clock(x), |x| Clock(x))

        # A message for a page that is no longer showing, like a late timer.
        _ => (model, [])
    }

render : Model -> Html(Msg)
render = |model|
    match model {
        Counter(c) => Html.map(Counter.view(c), |x| Counter(x))
        Clock(c) => Html.map(Clock.view(c), |x| Clock(x))
    }

Matching on the page and the message together means a message can only reach the page it belongs to. A page has one tag, Counter, in both unions, which Roc allows, so a row names the page and nothing else, and the two wrappers are the same lambda. Update.map is what makes each row one line. Html.map lifts a page's view into the app's messages, Effect.map and Sub.map do it for an effect and a subscription, and Update.map does it for what update returns, the model with its effects. It is a few lines you write once:

## What a page's `update` returns, in the app's types: its model in the
## page's tag, its effects' messages in the page's message tag.
Update := [].{
    map : (page, List(Effect(page_msg))), (page -> host), (page_msg -> host_msg) -> (host, List(Effect(host_msg)))
    map = |(page, effects), to_model, to_msg| (to_model(page), effects.map(|e| e.map(to_msg)))
}

The two wrappers are lambdas because a Roc tag is not a function: a bare Counter passed as an argument is the tag with no payload, not a constructor.

Two ways to switch pages

  • One URL per page (examples/pages). Links are ordinary links, the browser loads the next page, and the model only holds the page on screen. This is the shape of a server-rendered app.
  • Switching in place (examples/spa_pages). The app keeps every page's model and changes which one it shows, without a page load.

The page modules are the same in both. Only the app module differs, which makes the two examples easy to compare.

Both keep every page in one bundle, which a visitor downloads whole. That is right while the app is small. When it is not, a page can be a bundle of its own, or a server-rendered page with small bundles on it, with the same page modules. Bundles covers that.

Why pages get their own model

A page is the clearest case where its own model, messages and update pay off: pages have real state of their own and rarely share it. Do not take this as a pattern for everything else in an app. The section on picking the simplest API explains why.

Growing an app

Three folders: shared, client, server

A full-stack Joy app keeps its code in three folders, one for each place it runs. A page that runs in the browser lives at the same path in all three.

The Joy repository's examples/fullstack is a small lending library called Shelf, and the rest of this part follows it.

shared/

Compiled into both the browser and the server.

  • Each page's model, messages, view and endpoints
  • Routes, partials, and the components' models and views
  • Types and rules both sides use

client/

Compiled to WebAssembly. Only runs in the browser.

  • Each page's and component's init, update and subscriptions
  • The bundles, the Joy apps that run them
  • Sending requests to the server

server/

Compiled for the server. Only runs there.

  • Each page's handlers
  • The routing table
  • SQL, the HTML document around pages, and the views of pages the server alone renders
shared/Page/Books/Show.roc    Model, Msg, view, the endpoints
client/Page/Books/Show.roc    init, update, subscriptions
server/Page/Books/Show.roc    page!, borrow!, give_back!
client/main.roc               the bundle: Shelf's one Joy app, with every page in it

Pages are named by resource and action, like Page/Books/Index.roc for the catalog and Page/Books/New.roc for the form that adds a book. Knowing one half tells you where the other two are.

Which folder a function goes in

One rule decides it. If a function's type mentions Effect or Sub, it goes in client/, because those are types of Joy's platform and only a Joy app can import them. Everything else a page needs, its model, its messages, its view and its endpoints, goes in shared/, so the server can render the page from the same code the browser runs. Handlers and SQL go in server/. A page the server alone renders, with no state of its own in the browser, has no client half at all, and its view sits next to its handler in server/. Bundles says which pages those are.

The folders keep the sides apart

  • shared/ cannot import Joy's platform or the server's. A view in shared cannot do I/O, so both sides can render it.
  • client/ cannot reach the database.
  • server/ cannot use browser effects.

A wrong import does not compile, so the line between the sides is checked for you.

Importing by path

A module in a folder is imported by its path from the package root:

import /Page/Books/Show as PageBooksShow
import /Book

A bare import Book inside Page/Books/ would look for Page/Books/Book.roc, next to the importing file, which is why nested modules write import /Book. The shared package's main.roc gives each nested module a flat name, like shared.PageBooksShow, for the client and server to use.

Growing an app

Server rendering and hydration

The server sends a finished page, so the visitor sees it at once. Then the client starts and takes over that same markup instead of drawing it again. Joy calls this hydration, and what makes it safe is that the model itself travels.

On the server

  1. Read what the page needs, for example a book from the database.
  2. Build the page's model from it: the book, and the page's starting state, an empty form and status: Idle.
  3. Render view(model) to HTML.
  4. Put that markup inside a root that names the bundle and carries the model as JSON, with Html.bundle.

In the browser

  1. The loader, joy.js, finds the root that names the bundle and reads the model off it.
  2. It calls mount with it and hydrate: true.
  3. The bundle parses the model and hands it to the page's init, which returns it with the effects the page starts with.
  4. Its first render matches the server's markup, so Joy claims the existing nodes and attaches events to them.
<script type="module" src="/assets/joy.js"></script>
...
<div data-joy-bundle="main" data-joy-flags='{"Book":{"book":{"id":7,"title":"Emma", ...},"borrower":{"email":""},"status":"Idle"}}'>
  ...the book page, as the server rendered it...
</div>

The model is what travels

Hydration only works when both sides draw from the same data, and the simplest way to make that certain is to send the data. The server builds the model once, because it has to render it, and the browser starts from exactly that value. So view lives in shared/, the handler builds the model, and the client's init receives a model instead of building one:

page! : Ctx.Ctx, I64 => Try(Response, _)
page! = |ctx, book_id| {
    book = BooksSql.find!(ctx.db, book_id)?

    model : App.Model
    model = Book({ book, borrower: Borrower.empty, status: Idle })

    Layout.document(Html.bundle({ id: Bundle.path(Main), flags: Json.to_str(model), view: App.view(model) }))
}
## Elm's init: the model is the flags. It says what the page starts with, here nothing.
init : Shared.Model -> (Shared.Model, List(Effect(Shared.Msg)))
init = |model| (model, [])

Shelf keeps its pages in one bundle, so what travels is the app's union, Book(...) here, and the bundle's own init parses it and dispatches to the page. A page that is a bundle of its own sends its model bare. Either way there is no Flags type anywhere, and nothing builds a model but the server.

Why init takes the model

In a browser-only app init builds the model from the flags and names the effects to start with. In a full-stack app the server has already built the model, so there is nothing left to build. init receives it and says what the page starts with: a request, a timer, or nothing. It returns the model it was given.

The type lets it return another, and a page may do that knowingly when the browser knows something the server could not, the current time or the window size, at the price of a first render that differs from the server's. Joy repairs the difference and warns in the console, and the browser tests treat the warning as a failure, because an unintended one means the two sides disagree. The usual way is an effect: the first render stays the server's, and what the browser knows arrives as a message a moment later.

The model has to be data

What travels is written with Json.to_str and read back with Json.parse, and the compiler checks the model at those two calls. A model holding a function or a Box does not compile. Fractions are Dec, because an F64 can be NaN or infinite, which JSON cannot carry, and Json.to_str refuses an encoder that can fail. A type from a library is fine when the library gives it codecs, which in Roc is two lines inside the type that ask the compiler to derive them:

Carousel(slide) :: { id : Str, items : List(slide), position : U64, ... }.{
    parser_for : _
    encoder_for : _
}

Elm models can hold a navigation key or a time zone. These cannot, and that is the one habit to unlearn: what only the browser knows arrives through an effect, after the first render, and is kept in the model from then on.

The model is public

Everything in the model is in the page's source, whether the view shows it or not. Leave out what the visitor may not see. Shelf's Book.Detail has no field for who borrowed the book, so neither a book's page nor its model can carry the borrower's email.

Growing an app

Bundles

A bundle is a Roc app on the Joy platform: one file in your project, one wasm in the browser. Which bundles a page loads decides how much code a visitor downloads, and Joy lets you choose that page by page.

Three sizes, one mechanism

ShapeBundles on the pageRootWho routes
One bundle, every page inside1the whole pagethe client, or the server with one URL per page
A bundle per page1the whole pagethe server, one URL per page
Islands0 to neach island's elementthe server, one URL per page

Joy knows about none of this. ./joy build builds every bundle it finds, and the loader mounts every bundle root it finds on a page, so a page with one root around everything and a page with four small roots are the same to it. The choice is a size question. Shelf is small, so it is one bundle with its three pages inside. A shop whose checkout is a long interactive flow would make the checkout a bundle of its own. A product page that is mostly text, with a search box, a cart button and a review form on it, is a page the server renders, with three small bundles on it, each shared with every other page that shows it and cached by the browser.

A page lives where it runs

Kind of pageIts files
Interactive through most of its area: a search, a checkout, a dashboardshared/Page/X.roc with the model, messages, view and endpoints. client/Page/X.roc with init, update and subscriptions. client/x.roc, the bundle. server/Page/X.roc, the handlers.
Mostly text with a few interactive pieces on it: most pages of most sitesserver/Page/X.roc with the handler and the view together. Nothing in shared/ or client/: the interactive pieces are islands, which are components with bundles of their own.
A component, which is what an island isshared/Component/X.roc, client/Component/X.roc, client/x.roc, and its handlers in server/Component/X.roc.

Partials stay in shared/ even when only server-rendered pages use them today, because they are the pieces a bundle page is also built from.

Where bundles come from

./joy finds bundles by their headers: every .roc file in client/, at any depth, whose header is an app on the Joy platform. Modules, packages and apps on other platforms fall out on the first line. There is no manifest and nothing to register. A bundle's id is its path below client/, without the extension. Its output directory mirrors the id, and its tag follows from it:

./joy build
Bundle fileOutput directoryIdTag
client/catalog.rocdist/client/catalog/catalogCatalog
client/Checkout/cart.rocdist/client/Checkout/cart/Checkout/cartCheckoutCart
client/app.roc, a one-file appdist/client/app/appApp

Ids are paths below one fixed folder, so adding or removing a bundle never renames another. Naming a directory or a file, ./joy build client/Checkout, only picks what to build, and the ids stay the same. A Joy app outside client/, a test fixture say, is not built, and ./joy bundles lists it as found and not built. One loader, joy.js, sits next to the bundles with the runtime built into it, holding the browser code of every feature the bundles call, so a page loads one file. runtime.js is written beside it for anyone who imports mount by hand. A bundle's directory holds only its wasm.

A bundle file

Every bundle file is the same dozen lines, and ./joy new bundle writes them. What differs is which modules it names. A bundle for a page parses the model the server sent and hands everything to the page's two halves:

app [Model, Msg, init, update, render, subscriptions] {
    pf: platform "https://github.com/niclas-ahden/joy/releases/download/VERSION/HASH.tar.zst",
    html: "https://github.com/niclas-ahden/joy-html/releases/download/0.17.0/AcmwFzyfbsf5RALWNdX6cXw1cuuDXt96YfcysNqgFqoG.tar.zst",
    shared: "../shared/main.roc",
}

import /Page/Books/Index as Client
import shared.PageBooksIndex

Model : PageBooksIndex.Model
Msg : PageBooksIndex.Msg

init = |json|
    match Json.parse(json) {
        Ok(model) => Client.init(model)
        Err(e) => crash "Could not read the model: ${Str.inspect(e)}"
    }
update = |model, msg| Client.update(model, msg)
render = |model| PageBooksIndex.view(model)
subscriptions = |model| Client.subscriptions(model)

No annotations and no Effect, Sub or Html imports: the platform's requires pins the six types and the rest is inferred. A bundle for a component looks the same with the component's modules in place of the page's. A bundle contains what it imports and nothing else, which is the point: the review form's bundle has the review form, and no page.

On the page

A component that is used as an island offers one function, which puts its first markup inside a root that names its bundle and carries its model. The server page's view calls it where the island goes:

## The form on a server-rendered page: its markup in a root with its model.
island : Model -> Html(msg)
island = |form| Html.bundle({ id: Bundle.path(ReviewForm), flags: Json.to_str(form), view: ReviewForm.view(form) })
page! = |ctx, product_id| {
    product = ProductsSql.find!(ctx.db, product_id)?
    page = { product, review_form: ReviewForm.new({ product_id }) }
    Layout.document(view(page))
}

view = |page|
    Layout.page([
        product_details(page.product),
        ReviewForm.island(page.review_form),
    ])
<div data-joy-bundle="review_form" data-joy-flags='{"product_id":41,"text":"","status":"Idle"}'>
  ...the form, as the server rendered it...
</div>

The loader mounts every such root, loading the wasm whose URL Html.document gave the root, or the one in the <id>/ directory next to itself when it has none, and hydrating when the root has children. The same island twice on a page is two roots, two models and one cached wasm. A page that is one bundle has one root around the whole page.

The head needs the loader's script tag and a preload per wasm the page uses, in the fetch mode the runtime uses, so the browser fetches the wasm while the HTML still parses. Nobody lists them. Layout.document renders the page with joy-html's Html.document, which finds every root in the body, writes the hints itself and gives each root its wasm's URL, so a page that places an island gets its hint, and a page that stops placing it loses it. It takes the address your app serves client/ at and the build's names, which is how the same layout loads Joy's files under hashed names in production and plain names while you work, from the same place. The hints are an optimisation: a page without them is one round trip slower on a first visit, and the loader mounts whatever roots it finds either way.

Once a bundle is up, its root carries data-joy-mounted and root.joy is its handle, which is how a browser test waits for a page and how a page's own script reaches a bundle's ports.

The generated list of bundles

A page names a bundle with a tag, never a string, so a bundle that does not exist is a compile error. The tags come from ./joy build, which writes a package, generated/, from the bundle files it found:

Bundle : [Catalog, CheckoutCart, ReviewForm, ...]

path : Bundle -> Str     # CheckoutCart -> "Checkout/cart"

all : List(Bundle)

Your server and your shared package depend on it by path, like any package. It is committed, like a generated schema. ./joy build and ./joy dev rewrite it, only when it changes, and ./joy doctor says when it is stale. It is written when a header in the project names it, and only then: a full-stack app's server names it from the start, and a client-only app gets it the day one of its bundles names a file in assets/ or public/. A one-file app whose page is HTML in public/ never grows one. Rename a bundle file and the pages that name it stop compiling, which is what you want.

It is made from the bundle files alone, before anything compiles, so the server and the bundles build at the same time.

Islands share the document

Two bundles on one page share no model. What they share is the DOM, and that decides where an island's edges go. The rule: a region is one island when its parts need one model. A dialog and the button that opens it are one island, with the root where the button sits and the <dialog> rendered by the same bundle, which works because a dialog is top layer and its place in the DOM does not matter. A list of bookable showings and the booking dialog their buttons open are one island. A form whose thank-you view embeds another form is one island with the second form embedded as a component.

What remains between islands goes through the document, as it already does inside one app: DOM.show_modal("#id") opens a dialog whoever owns it, and a keyboard subscription hears a key whichever island asked. Two islands listening for Escape are fine as long as each checks its own state first. If two islands ever had to share a value, the mechanism would be a document event, and the better answer is nearly always to make them one island.

One bundle per island type, not one for all of them. A page then downloads the islands it places and nothing else, each cached across the whole site, and every bundle stays a single component with no wiring inside. Memory is the same either way, one instance per root, which is also why a page should have a few islands and not twenty.

Growing an app

One type for every URL

Every URL the app answers is a tag of one type. The server turns a request into a route with parse, and every link and request is built from a route with to_path.

Route := [].{
    Route : [
        ## `/`, or `/?q=austen` with a search.
        Catalog({ query : Str }),
        ## `/books/7`
        Book(I64),
        ## `/books/new`
        NewBook,
        ## `/api/books/7/loan`
        ApiLoan(I64),
    ]

    parse : Str -> Try(Route.Route, [NotFound])

    to_path : Route.Route -> Str
    to_path = |route|
        match route {
            Catalog({ query }) => with_param("/", "q", query, "")
            Book(id) => "/books/${id.to_str()}"
            NewBook => "/books/new"
            ApiLoan(id) => "/api/books/${id.to_str()}/loan"
        }
}

expect Route.parse(Route.to_path(Book(7))) == Ok(Book(7))

A link is then a([href(Route.to_path(Book(book.id)))], [text(book.title)]), never a string you type by hand. Each URL is spelled in exactly one place, and the expect lines hold parse to be the inverse of to_path.

Rename a URL and every link follows. Remove a route and every link to it stops compiling.

Growing an app

The routing table

On the server, one match on the route decides how every request is answered. It is exhaustive, so a new route does not compile until it has a row.

route! : Server.Request, Context, Route.Route => Try(Response, _)
route! = |req, ctx, route|
    match route {
        Catalog({ query }) => Routing.get!(req, || ServerBooksIndex.page!(ctx, query))
        Book(book_id) => Routing.get!(req, || ServerBooksShow.page!(ctx, book_id))
        NewBook => Routing.get!(req, || ServerBooksNew.page!())

        ApiLoan(book_id) =>
            Routing.api!(req, [
                ApiServer.on(PageBooksShow.borrow(book_id), |borrower| ServerBooksShow.borrow!(ctx, book_id, borrower)),
                ApiServer.on(PageBooksShow.give_back(book_id), |{}| ServerBooksShow.give_back!(ctx, book_id)),
            ])
    }

Each row answers in one of three ways:

  • get! for anything fetched with GET: a page, a redirect, a file. HEAD is answered like GET.
  • api! for a route's JSON endpoints, each with its handler. The endpoints decide which methods the route takes.
  • raw! for a route that reads the request itself, like a file upload.

Any other method gets a 405. The rest of main.roc is configuration.

Who may use a route

In an app with sign-in, give each row an access level as a tag around its handler:

Loans => get!(req, ctx, AnyAdmin(|user| ServerLoansIndex.page!(ctx, user)))
Catalog({ query }) => get!(req, ctx, Public(|| ServerBooksIndex.page!(ctx, query)))

No row can leave the level out, and a handler gets the signed-in user exactly when the level means there is one.

Where these come from

Route, Routing, Api, ApiServer and ApiClient are modules of the Shelf example, not part of Joy itself. They are small. Copy them into your app and change them to fit.

Growing an app

Typed endpoints

A JSON endpoint is defined once, in the page's shared module, with its request, its answer and its errors as types. The server and the client are both held to it.

BorrowError : [BookMissing, AlreadyOnLoan, BadEmail(Str), Server(Api.Failure)]

borrow : I64 -> Api.Endpoint(Book.Borrower, Book.Detail, BorrowError)
borrow = |book_id|
    Api.post(
        Route.to_path(ApiLoan(book_id)),
        |error|
            match error {
                BookMissing => 404
                AlreadyOnLoan => 409
                BadEmail(_) => 422
                Server(failure) => Api.failure_status(failure)
            },
    )

The server's handler

A handler takes the decoded request and returns the answer or one of the endpoint's errors. It reads no body, sets no status and builds no JSON. ApiServer.on does all of that.

borrow! : Ctx.Ctx, I64, Book.Borrower => Try(Book.Detail, PageBooksShow.BorrowError)
borrow! = |ctx, book_id, submitted| {
    borrower = Book.check_borrower(submitted) ? |why| BadEmail(why)
    _ = BooksSql.find!(ctx.db, book_id)?
    now = UnixTime.now!().seconds_since_epoch()
    LoansSql.borrow!(ctx.db, { book_id, email: borrower.email, now })?
    BooksSql.find!(ctx.db, book_id)
}

The client's side

The client sends with the endpoint, and the answer arrives as a message carrying a Try, which the page matches like any other value:

UserSubmittedBorrow =>
    ({ ..model, saving: Saving }, [ApiClient.send(PageBooksShow.borrow(model.book.id), borrower, |answer| ServerAnsweredBorrow(answer))])

ServerAnsweredBorrow(Ok(book)) => stored(book)
ServerAnsweredBorrow(Err(AlreadyOnLoan)) => (failed(model, "This book is already on loan."), [])
ServerAnsweredBorrow(Err(BadEmail(why))) => (failed(model, why), [])
ServerAnsweredBorrow(Err(BookMissing)) => (failed(model, "This book is no longer in the catalog."), [])
ServerAnsweredBorrow(Err(Server(failure))) => (failed(model, Api.failure_text(failure)), [])

Rename a field on one side and the other stops compiling. Add an error to BorrowError and the page does not compile until it has words for it. A handler cannot return an error the endpoint does not list.

Server(Api.Failure)

Every endpoint's errors end with Server(Api.Failure): anything that went wrong that is not one of its own errors. It covers no answer at all, a timeout, an answer the page cannot read, and on the server side a service that is briefly out, a failing upstream and plain bugs. The page usually has one set of words for all of them and matches a single case when it has better ones.

A Server failure loses its details on the way out. The browser gets a status and a short error, never the database's message.

Structuring for scale

Pick the simplest API

When a piece of UI shows up in more than one place, first ask what its API should look like. Then pick the simplest one that does the job.

This is the central idea of Richard Feldman's talk Scaling Elm Apps, and it holds for Joy the same way. There is a ladder of APIs, from simple to heavy. Each step up costs more to use, so climb only as far as you need.

  1. 1

    A value

    Nothing changes from one use to the next.

    subscribe_button : Html(msg)
subscribe_button = a([class("button"), href(Route.to_path(Subscribe))], [text("Subscribe")])
  2. 2

    A function of data

    It shows different things, but does nothing on its own.

    badge : User -> Html(msg)
badge = |user| span([class("badge")], [text(user.name)])
  3. 3

    Teach it how to message

    It reacts to the user, and the caller says which message to send. The caller keeps the state.

    checkbox : { label : Str, checked : Bool, toggled : msg } -> Html(msg)
checkbox = |{ label: words, checked: is_checked, toggled }|
    Html.label([], [
        input([type("checkbox"), checked(is_checked), on_click(toggled)]),
        text(words),
    ])
  4. 4

    Its own model, messages and update

    It has state of its own and several messages with real logic behind them, and you would otherwise repeat all of that on every page that uses it. This is a component.

    ContactForm.Model, ContactForm.Msg, ContactForm.init, ContactForm.view   # shared
ContactForm.update                                                   # client

Why not make everything a component

Coming from React or object-oriented UI, it is tempting to give every piece of the page its own model, messages and update, so they all look alike. Feldman tried that early on and was unhappy with it, and so were many others. It goes wrong in three ways:

  • It splits the truth. Give every dropdown its own open : Bool and two of them can be open at once, though the design says only one may be. Store open_dropdown : [NoDropdown, Open(DropdownId)] in the page instead, and the bug cannot be written.
  • It widens every type. A button that could be Html(msg) now needs an init, a message type, an update branch in every page and a Html.map.
  • It needs parent-child plumbing. Once state lives in a child, the parent keeps needing pieces of it back, and you write code to pass them up.

Feldman's comparison is a place setting: soup takes a spoon, salad a fork, chicken a fork and a knife. Using every utensil for every dish is not more consistent, only harder. Each piece of UI gets the tool that fits it.

Structuring for scale

Partials

A partial is a piece of view that several pages show: a header, a footer, a list of results. It has no state and no update of its own. It is a function, on the first three steps of the ladder.

Menu := [].{
    ## Which entry is the current one.
    Section : [Catalog, Loans, NewBook, Nowhere]

    view : Section -> Html(msg)
    view = |current|
        header([class("top")], [
            nav([class("links")], [
                entry("Catalog", Catalog({ query: "" }), current == Catalog),
                entry("On loan", Loans, current == Loans),
                entry("Add a book", NewBook, current == NewBook),
            ]),
        ])
}

The menu is built only from what it is given, and its type, Html(msg), says it sends nothing. The app's pages show it, and so do the server's 404 and 500 pages, so the whole site has one header.

Let the caller name the messages

When a partial has buttons, let the caller pass the messages in. Do not write the page's message tags inside the partial.

# Ties the partial to one page: it only works where Msg has Booking(Opened(_)).
showings : List(Showing) -> Html(_)
showings = |list| ul([], list.map(|s| li([], [button([on_click(Booking(Opened(s.id)))], [text(s.time)])])))

# Works for any page, and the type shows what it can send.
showings : List(Showing), (I64 -> msg) -> Html(msg)
showings = |list, book| ul([], list.map(|s| li([], [button([on_click(book(s.id))], [text(s.time)])])))

The second version is the same idea as on_click itself: the element does not know your messages, you tell it which one to send. A partial that names a page's tags looks reusable but only works on that one page.

Structuring for scale

Components

A component is a piece of UI with its own model, messages and update, used inside pages or placed on them as an island. Think of it as a page without a URL. Use one only at the top step of the ladder.

When it pays off

A contact form shown on many pages is the typical case. It has several fields with validation, a submit that sends a request, and success and error states. Without its own Msg and update, every page that shows it would need all those messages and all that logic. With them, each page keeps one field and one message tag, or places it as an island and keeps nothing. Feldman's elm-spa-example does the same for its article feed, used on two pages and with six messages of its own.

It does not pay off for something used on one page. Keep that inside the page. It also does not pay off for something with one or two messages and little logic. Give it the messages as arguments instead.

Its shape

A component has the same halves as a page, at the same path, plus a bundle when it is an island:

shared/Component/ContactForm.roc    Model, Msg, new, view, island, its endpoint
client/Component/ContactForm.roc    init, update, subscriptions
server/Component/ContactForm.roc    the handler of its endpoint
client/contact_form.roc             its bundle, when it is an island

What differs between two uses goes into new, like where the form posts, and stays in the model. The server, or the page that embeds the form, builds it with new. Then init says what it starts with and update takes the model and the message and nothing else:

new : { posts_to : Route.Route } -> Model

init : Model -> (Model, List(Effect(Msg)))

update : Model, Msg -> (Model, List(Effect(Msg)))

Embedded in a page

A page that is a bundle keeps the component's model in one field and wraps its messages in one tag named after it:

Model : { listing : Listing, contact_form : ContactForm.Model }

Msg : [UserClickedFavorite, ContactForm(ContactForm.Msg)]

Update.map, from Pages, puts the component's result back into the page the way it puts a page's result back into the app:

# in the page's update:
ContactForm(form_msg) =>
    Update.map(ContactForm.update(model.contact_form, form_msg), |form| { ..model, contact_form: form }, |m| ContactForm(m))

As an island

On a page the server renders, the same component is a bundle of its own. The page keeps nothing of it: the handler builds the form with new, the view places it with the component's island, and client/contact_form.roc runs it in the browser. The component's halves are the same either way, and the choice is the page's: embedded when the page is a bundle, an island when the page is text with the form on it. Bundles has the whole picture, including why a dialog island owns its own button.

Telling the page something

Sometimes a page that embeds a component has to react to what happened inside it. Say the form sits in a dialog that the page owns, and the form's "No thanks" button should close it. Let update return what the page needs to know:

update : Model, Msg -> (Model, List(Effect(Msg)), [Stay, Close])

# in the page:
ContactForm(form_msg) => {
    (form, effects, outcome) = ContactForm.update(model.contact_form, form_msg)
    closing =
        match outcome {
            Close => [DOM.close_modal("#contact")]
            Stay => []
        }
    ({ ..model, contact_form: form }, effects.map(|e| e.map(|m| ContactForm(m))).concat(closing))
}

Two other ways show up in real code and age badly:

  • The page matches the component's own messages, like ContactForm(Closed). Now the page depends on how the component is built inside, and a renamed message breaks it.
  • Configuration that says one thing while the page does another. If the form is told in new that it closes its own dialog, but the page catches that message first, the configuration is never read and misleads the next reader.

A returned outcome is part of the component's API, in its type, and the compiler checks every page that uses it. As an island the question does not arise: the island owns its dialog and closes it itself.

Structuring for scale

State as types

When something can be in one of a few states, write those states as a tag union. Then the states that make no sense cannot be written at all.

Booleans that can contradict each other

# Two flags and an error text that can contradict each other:
# sending and sent at once, an error after success.
Model : { sending : Bool, sent : Bool, error : Str }

# Exactly the four states there are.
Status : [Editing, Sending, Sent, Failed(Str)]
Model : { status : Status }

The view now matches on status, and the compiler makes sure every state has a view. Shelf does this for the catalog's search, [Done, Searching, Failed(Str)], and for a book page's request, [Idle, Saving, Failed(Str)].

No placeholder values

An empty string for "nothing chosen" or a 0 for "closed" are states the type does not know about. Name them instead:

# A booking dialog with placeholders:
# showing_id 0 means closed, slot_id "" means nothing picked,
# and loading, error and slots can all be set at once.
Booking : { showing_id : I64, slot_id : Str, loading : Bool, error : Str, slots : List(Slot) }

# The same dialog with its states named:
Booking : [Closed, Open(Dialog)]

Dialog : { showing : Showing, slots : Slots, contact : Contact, status : Status }

Slots : [Loading, LoadFailed(Str), Loaded(List(Slot), Step)]

Step : [Picking, Picked(Slot), Details(Slot)]

Now a slot can only be picked once the slots have loaded, and the details form can only be filled in for a chosen slot. The view and the update match on these states, and there is no state left for the code to forget.

One source of truth

Keep each fact in one place and compute the rest. Whether the form can be sent is a function of its fields, not another field that has to be kept in step:

is_complete : Contact -> Bool
is_complete = |c| !Str.is_empty(c.name) and is_valid_email(c.email) and c.consent

Feldman's talk Making Impossible States Impossible walks through this way of thinking in depth.

Structuring for scale

Narrow types

As an app grows, the way to keep it understandable is to keep less in your head. Functions that take only what they need, and return only what they change, do that for you.

Take only what you need

# Can read and change anything in the model.
view_header : Model -> Html(Msg)

# Can only show a user and a count, and sends nothing.
view_header : User, U64 -> Html(msg)

The narrow version is easier to reuse, and it helps when debugging. When a field of the model goes wrong, any function whose type does not mention that field cannot be the cause, so you can skip it without reading it.

The same goes for parts of update. A helper that changes only an address should take and return an address:

update_address : AddressMsg, Address -> Address

When a page has many messages for one part of it, group them in a union of their own, like Booking(BookingMsg), handled by a function that takes only that part's state. That is organisation, not a component: the part stays in the page.

Give ids their own types

When a book's id and a loan's id are both I64, nothing stops you from passing one where the other belongs. An opaque type makes that a compile error:

BookId :: { value : I64 }.{
    from_i64 : I64 -> BookId
    from_i64 = |n| { value: n }

    to_i64 : BookId -> I64
    to_i64 = |id| id.value
}

Outside the module, a BookId can only be made with from_i64, and code that wants one cannot be handed a LoanId by mistake. The same works for a URL to post to: take a Route.Route, not a Str, and only real URLs of the app can be passed in.

Write the types out

Annotate the functions other modules call, with real types rather than _ holes. The annotation is the documentation readers see first, and it keeps a mistake inside the module that made it instead of surfacing as a confusing error somewhere else.

Structuring for scale

Messages are facts

Name a message for what happened, in the past tense, and say who did it. Leave it to update to decide what that means.

# Commands: says what should happen, which is update's job.
Msg : [SetEmail(Str), Submit, SaveBook]

# Facts: says what happened.
Msg : [
    UserTypedEmail(Str),
    UserSubmittedBorrow,
    UserPausedTyping,
    ServerAnsweredBorrow(Try(Book.Detail, BorrowError)),
]

Facts read well in a log of messages, and one fact can mean different things in different states. A UserPressedEscape can close a dialog when one is open and do nothing otherwise, which a CloseDialog command would not let you say.

A message that wraps a child's messages is named after the child, the same tag the model uses for it: Counter(Counter.Msg) for a page whose model is Counter(Counter.Model), ContactForm(ContactForm.Msg) for a component kept in contact_form. Roc lets two unions share a tag, so a page has one name wherever it appears.

Structuring for scale

Organizing modules

Build each module around a type, keep the tree flat, and use headings inside a module instead of splitting it into many files.

  • Start in one file. Evan Czaplicki's talk The Life of a File shows how a module grows: add to it until a type with its own functions clearly emerges, then move that type and its functions into a module of their own.
  • A module is a type and its functions. Book.roc has the book types and the rules about books. Route.roc has the routes. Name modules after what they are about, not after what kind of code they hold.
  • Long files are fine. In Roc, as in Elm, the compiler makes it safe to move code around later, so a 600-line module is not a problem by itself. Split when there is a type to split out, not to make files shorter.
  • Use headings. A comment heading is enough to organise a module, the way a document has sections.
# Model

# View

# Form

# HTTP
  • Same path in every folder. In a full-stack app a page's three halves sit at the same path in shared/, client/ and server/, so finding one finds them all.
  • A bundle file names modules and holds nothing else. It sits at the top of client/, or anywhere under it, and delegates every one of its six parts to a page's or a component's modules. Logic in a bundle file is logic no other bundle can reuse.
  • Rules both sides check live in shared. Shelf's Book.check_borrower runs in the browser before the form is sent, so a mistake shows at once, and again on the server, because a request can come from anywhere. Both say the same words about the same mistake.

Reference

Adding a page

In a full-stack app, adding a page is a fixed list. The compiler checks each step and points you to the next one.

  1. A tag in Route.Route, with its arms in parse and to_path.
  2. Decide its shape, from Bundles: a page in an app that is one bundle, like Shelf; a bundle of its own; or a page the server renders with islands on it.
  3. For the first two: shared/Page/<Resource>/<Action>.roc with the page's model, messages, view and endpoints, and its line in shared/main.roc. For a server-rendered page: nothing here.
  4. server/Page/<Resource>/<Action>.roc with the handler that builds the model and sends it, its endpoints' handlers, and its row in the routing table. A server-rendered page keeps its view here too, and builds each island's model with the component's new.
  5. For the first two: client/Page/<Resource>/<Action>.roc with init, update and subscriptions. In a one-bundle app, its tags in the app's model and messages and its rows in the app's matches. As its own bundle, ./joy new bundle client/<name>.roc. A running ./joy dev sees the new file and adds its tag to generated/Bundle.roc, and so does the next ./joy build.
  6. An entry in the menu if it needs one.

Try it on Shelf: add an author page at Page/Authors/Show.roc and let the compiler walk you through the rest.

Reference

The ./joy command

Every Joy project has ./joy in its root, a small program that knows which release the project is on. It finds the bundles in client/ by their headers and never needs to be told which they are.

Getting it

Make a folder for your project, and run roc run --opt=speed <the CLI's release URL> init in it. It shows the templates the release ships, a single-page app and a full-stack app with no database, SQLite or Postgres, lets you pick one with the arrow keys, writes it and installs ./joy. --template <name> picks one without asking, which is how a script or CI does it. In a directory that already has an app, init only installs ./joy, and then checks that your Roc matches the release. ./joy is built for your machine, so it goes in .gitignore, and so does .joy/, where it keeps what it makes while you work.

While you work: ./joy dev

./joy dev builds every bundle and keeps them up to date as you save. It rebuilds only the bundles a change reaches: roc reports which files each build read, so a change in one component rebuilds one bundle and a change in a shared view rebuilds every bundle that uses it. Open pages take a new build without a reload and keep their state, because the new build replays the messages the page has seen so far. A build that fails shows roc's report over the page until one succeeds. Bundles build at --opt=size, like the ones that ship, since roc's dev backend can make a wasm too large for the browser to compile, and a server ./joy dev starts builds at --opt=dev, which takes seconds.

Its builds go to .joy/dev/, never to dist/. ./joy build can run at the same time, from a test run say, and a build made for hot reloading can never be deployed by mistake. .joy/dev/ holds only what ./joy dev builds, joy.js and the bundles, and an assets.json whose names are all plain and which says where each file lives. public/ and assets/ are served from where they are, so nothing is copied and a file is served the moment you save it. Development and production differ in the names alone, so a page loads its files from the same addresses in both.

Who serves the pages depends on the project:

The projectWhat ./joy dev runs
has no serverA server for public/, assets/ and the bundles, at http://localhost:8000 or the next free port. A path without an extension answers index.html, so an app that changes the URL survives a refresh.
has server/main.rocYour server, serving the files .joy/dev/assets.json lists, rebuilt and restarted when a file it reads changes, and a dev server of its own for the reload events.
is started with --server FILE, as often as neededThose servers instead of server/main.roc, started and stopped together.
is started with --no-serverOnly the dev server, for the reload events. Your own server, run on its own, points itself at .joy/dev/assets.json.

A server that ./joy dev starts finds .joy/dev/assets.json in JOY_ASSETS_JSON and serves the files it lists from where they are, as it serves the files of dist/assets.json from dist/client/ in production. Nothing else in your server knows it is in development.

When you change a file in public/ or assets/, open pages do what fits how they used it:

What changedWhat the page does
a stylesheet linked from outside any bundle root, usually in the headTakes the new styles in place, without a reload, so nothing on the page changes but the styles.
anything else the page loaded: an image, a script, a font, a page in public/Reloads, and replays what you did, as after a server change.
a file the page never loadedNothing.

A reload asks for the same plain names again, so whatever serves the files in development must make the browser revalidate with Cache-Control: no-cache, or a reload can show an old copy. basic-webserver's file serving does that by default, and the dev server too. A proxy in front, like Caddy, needs the header added in development, and the console warns when it is missing.

When your server changes, open pages reload once the new server answers, and each bundle replays what you did on the new markup, so typed text and open dialogs stay. Requests are not replayed from the recording, because the server that answered them is the one you just edited. A GET that is the same as before is sent again and the replay goes on with the new answer. Any other GET is sent and ends the replay. Anything else, a POST say, ends the replay before it, so nothing is sent twice. The console says where the replay stopped and why.

A client-only app whose data comes from a backend of its own, a Rails or a Go API say, can have ./joy dev forward its requests, so the app calls the same /api paths while you work as in production, and the backend needs no CORS headers:

$ ./joy dev --proxy /api=http://localhost:3000

--proxy can be given as often as needed. It forwards whole answers, so streamed answers, server-sent events and WebSockets do not go through it. A setup with several backends puts a reverse proxy like Caddy in front instead.

--no-hot builds what ships instead, and the page reloads after each rebuild. Reach for it when a bug might live in the difference: a hot build records every message, and its wasm is larger.

Ports

SettingWhat it is
JOY_PORT, --portWhere ./joy dev serves your pages in a project without a server. 8000, or the next free port.
JOY_DEV_SERVER_PORT, --dev-server-portThe dev server's port when your own server serves the pages. By default the system picks a free one from the range it keeps for that, so it never takes 8000 or a port your servers are likely to use, and ./joy asks for the same one next time, so open pages reconnect after a restart. Set it when your server runs on its own and has to know it.
JOY_HOST, --hostThe address to listen on, localhost by default. Set it to open the pages from a phone.

What ships: ./joy build

./joy build [--debug] [--opt=LEVEL] [--out-dir DIR] [--public-dir DIR] [--jobs N] [--no-server] [--server-opt=LEVEL] [--server-target=TARGET] [DIR|BUNDLE...] [-- ROC FLAGS] builds what you deploy. It empties the output directory, dist/ unless --out-dir names another, copies public/ into its client/ as it is and assets/ under hashed names, builds the bundles there, writes joy.js with the browser code of exactly the features they call, and prints each bundle with its size. Bundles build at --opt=size, which in Joy's benchmarks makes the smallest wasm without running slower, unless --opt picks another level. Bundles that need different levels go to different output directories, one run each.

joy.js and every wasm are named by a hash of their content, so a host can cache them for good and a deploy never leaves a page on a stale wasm. In the HTML files it copies from public/, the build rewrites the references to joy.js and to files in assets/ to the hashed names, and gives each bundle root on the page its wasm's URL and a preload. Your pages keep saying ./joy.js, which is what ./joy dev serves.

Your own files go in one of two folders, and the folder decides what the build does with them:

FolderForIn a build
public/Addresses other people hold, like robots.txt, favicon.ico and a PDF linked from emails, files someone else named or hashed already, and large media.Copied byte for byte, at the same path. Never read and never hashed.
assets/What your own pages link to and nothing outside does: stylesheets, fonts, images, scripts.One copy each in dist/client/, at its own path with a hash of its content in its name, css/site.3f9a1c2b.css. A stylesheet's url() to another file in assets/ is rewritten to the hashed name.

Roc code names a file with a string literal that the compiler checks, Asset for assets/ and Public for public/, so a misspelled name is a compile error. An asset gets its hashed name in a build and the plain one while you work, so editing a stylesheet rebuilds nothing. Say once where client/ is served, the same address while you work and in production, and pass the same one to Html.document:

client_url : Str
client_url = "/"

asset : Asset -> Str
asset = |file| "${client_url}${Asset.path(file)}"

link([rel("stylesheet"), href(asset("css/site.css"))])

A file in assets/ that names other files in a way the build does not rewrite, like a web app manifest's icons, is better served by your server, which names its files through Asset, or goes into public/ together with the files it names.

A server writes the script tag, the preloads and the roots' wasm URLs itself, so it needs the hashed names too. When the project has server/main.roc, ./joy build builds the server at the same time as the bundles, at --opt=speed. Every build writes the hashed names into dist/assets.json, the name of joy.js, of each bundle's wasm and of each file in assets/, as plain JSON that any other tool can read too. The binary goes to dist/server/main, beside dist/client/, which holds everything public. Your server serves dist/client/, never dist/, so its own binary can never be downloaded, and you deploy dist/ as one unit. The server reads assets.json when it starts, and the layout passes it to Html.document with the address client/ is served at. The server answers a path that matches none of its pages by looking it up there, so the files can sit at the root next to your pages, each with its own cache policy: a year for a hashed name, revalidate for a plain one. While you work it reads the one in .joy/dev/, with plain names. A server that finds no assets.json, or one that misses one of its bundles or was made for other assets, stops at startup and says why, so a deploy that does not belong together fails at once.

  • --server-opt picks another level for the server, and --server-target cross-compiles it, for a Linux server built on a Mac say.
  • --no-server builds the bundles alone. A server built some other way, in a Nix derivation of its own say, compiles with the flag ./joy build prints and reads the build's assets.json from the file JOY_ASSETS_JSON names.
  • A project has one server that renders its pages. Two servers that serve different bundles, a public site and an internal portal say, are two Joy projects side by side, each with its own client/, server/ and ./joy, sharing views and types through a package both name by path. Each server can then only name its own bundles, and a typo is a compile error.

A static host publishes dist/client/, and needs to answer index.html for an app's own paths: Netlify with /* /index.html 200 in _redirects, while Cloudflare Pages does it for a site without a 404.html.

  • --debug writes the whole runtime, readable and with every feature, and asks roc for debug information. It is for chasing a bug.
  • --jobs builds that many bundles at a time, 4 by default.
  • A warning in your own files fails the build, and the warnings of downloaded packages are only printed. ./joy dev prints warnings and carries on.
  • Anything after -- goes to roc as it is, -- --no-cache for instance.
  • The same file in public/ and assets/, or a file at a path Joy writes, like joy.js, fails the build instead of one of them silently winning.

The output directory belongs to ./joy, which empties it on every build. It refuses a directory outside the project, the project itself or a parent of it, and a directory with files in it that it did not make, so a mistyped --out-dir cannot delete your own files.

In tests

Tests run what ships, so a test run is a build into a directory of its own, ./joy build --out-dir .joy/test/<run>, with --debug or another --opt for a second pass. Each run gets a new directory, so two passes back to back never mix, and two runs at once never replace each other's files. The directory records how it was built, which a test harness checks before it starts a browser. A run deletes its directory when it ends, and ./joy removes the ones left by runs that died. Tests never use the builds of ./joy dev. A run that builds a server gets one of its own in its directory's server/, which reads the run's assets.json, and a harness with several passes can build the server once and point it at each pass's assets.json with JOY_ASSETS_JSON.

Bundles

  • ./joy new bundle <path> writes a bundle file.
  • ./joy bundles lists the bundles, their ids and their outputs, and the Joy apps outside client/ it does not build. --json prints the same for a backend in another language or a test harness.

Releases

  • ./joy versions lists Joy's releases with their dates and the Roc each recommends, and marks the one the app and ./joy are on.
  • ./joy use <tag> moves the app to a release: it builds that release's CLI first, then rewrites the Joy platform URL and the joy-html URL in every .roc file that names them: the bundles, the server, the shared package, tests and scripts. It also rewrites the packages the project names by path outside it, and says which, so a second project that shares them can follow. If the build fails, the app is left alone.
  • ./joy doctor shows the app's release, says when a newer one is out, compares your Roc with the recommended one, and reports the bundles it found, their outputs and whether generated/ is current. It also lists the files outside client/ on another Joy release than the app, and the files on another joy-html release than the rest.

./joy always runs the CLI of the app's release, because the two have to agree on how the runtime is put together. When your app is on another release than the one ./joy was built for, it builds that release's CLI into .joy/cli/, once, and hands the command over to it. It never asks, since that changes none of your files, and it says so:

./joy 0.15.0 is running Joy 0.14.0, the release this app is on.

So an old commit, a teammate with an older ./joy and CI all get the CLI the app was written for. Moving the app to another release is always your call, with ./joy use. Bundles on different releases share one joy.js, so they have to agree too: the build lists each bundle with its release and prints the ./joy use command that moves them all to the newest one.

./joy build and ./joy dev download nothing themselves. Roc fetches the platform and the packages the first time it needs them, from the internet, or from a cache filled beforehand in a Nix build, so the same commands work in both.
